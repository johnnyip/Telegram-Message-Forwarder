# Media reliability — 2026-11-19

## Incident and changes
- Non-file link previews (MessageMediaWebPage/Empty without a photo/document) follow text policy. Other non-file payloads produce source/message/class-specific unsupported diagnostics before allocating spool. Genuine files keep immutable revision identity; no fabricated revision fallback.
- Media captions, including timestamp/navigation additions, are conservatively bounded to 1024 raw UTF-16 units. Truncation preserves header/footer, emits caption_bounded length-only diagnostics, and sends plain text to avoid broken Markdown. Full original source_text remains in the queue and edit mapping; no additional side-effecting overflow message is sent.
- Sending retries only definite RetryAfter once and at most 60 seconds. Invalid-format representations may fall back only after selected BadRequest rejections. Timeout/5xx/connection failure is uncertain: no automatic upload retry, format change, or topic-to-general resend. This cannot prevent Telegram upstream faults or prove whether an old timeout was delivered.
- New immutable per-copy receipts distinguish target/topic/general and source revisions. Partial progress survives a later rejection. Existing parent operation codec/claims/receipts remain unchanged. Missing/partial API message IDs never count as delivery proof. Historical claims are NOT reset/migrated automatically.
- Every failed media consumer job is durably classified send_failed_recoverable with a critical media_delivery_unconfirmed event including source message, fingerprint and Kafka coordinates. Existing spool files/unknown delivery claims remain retained; later source traffic can progress without repeated uncertain sends. This is not a no-loss or exactly-once guarantee; retained incidents still require bounded reconciliation.
- Future-comment errors now record sanitized message, phase, source, cursor, pending state, capped exponential retry (15s through 300s in default deployment), and explicit recovery events. State saves refresh the existing owned lease atomically. Policy disable/route changes bypass backoff; cursor/generation/evidence fences are unchanged. Previous generic RuntimeError logs lack a reason and cannot be retrospectively attributed; live state was already recovered before this release.

## Verification
Focused regression covers non-file previews, UTF-16/emoji captions, file/album preflight, safe parse fallback, RetryAfter limits, no network resend, per-copy replay/target separation, uncertain/incomplete receipt fences, and future-comment durable backoff/recovery. Full native suite and normal Jenkins Python image build suite are supplemental to PRD source→snapshot→Kafka→Telegram response/commit correlation. Do not infer delivery from process health or offset progress alone.

## Deployment and rollback
Canonical code folder remains the existing GB10 main checkout (no SIT branch exists). Use the existing TG Message Forwarder Pipeline; no independent/manual helper container or image build. After immutable publication, change only the shared forwarder image digest in the canonical homelab-config compose file, publish an isolated release tag, and Git-redeploy stack22/NAS7 preserving routes, env, mounts, sessions, spool, Kafka offsets, bot identity and other service images. Check actual effective image/revision and configuration parity.
Rollback selects the previous exact compose tag/digest using Git ownership. Do not clear Redis claims, reset offsets, delete SQLite, or sweep retained files as rollback. Historical ambiguous sends require source/destination evidence; uncertainty is not permission to resend.
